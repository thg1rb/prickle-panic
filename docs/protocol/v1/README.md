# WebSocket Protocol v1

## Status and source

The JSON Schema in [`message.schema.json`](message.schema.json) is the machine-readable v1 contract for the initial Speed Battle protocol. It follows `docs/REQUIREMENT.md` §19 and leaves Guest Session HTTP creation, connection lifecycle, and gameplay authority to the relevant later Work Items. Player-facing errors are rendered by the client in Thai; protocol error objects carry stable codes rather than display text.

The `variant` value is an integer from 0 to 31 for transport. Its five bits map to the requirement's attribute order (body color, quills, glasses, scarf, strawberry), most significant bit first. This is a technical encoding convention; it does not change the attribute values or matching rule.

## Envelope and message catalog

Client requests use `{ "v": 1, "type": ..., "requestId": ..., "payload": ... }`. Server state events use `{ "v": 1, "type": ..., "requestId"?: ..., "seq": ..., "payload": ... }`. Server errors use `{ "v": 1, "type": "error", "requestId"?: ..., "payload": { "code": ..., "retryable": ... } }`.

| Direction | Type | Purpose |
|---|---|---|
| Client → server | `room.create` | Create a private Room for the authenticated Guest Session. |
| Client → server | `room.join` | Join by Room Code. |
| Client → server | `room.leave` | Leave the current Room. |
| Client → server | `room.set_ready` | Set Lobby readiness. |
| Client → server | `match.start` | Request Host-authorized Speed Battle start. |
| Client → server | `game.pick_card` | Submit a card selection with match, board, and reference versions. |
| Client → server | `state.request_snapshot` | Request resynchronization after a sequence gap or reconnect. |
| Server → client | `room.snapshot`, `room.updated` | Authorized Room/Lobby state. |
| Server → client | `game.snapshot` | Per-player Match state after connect/reconnect. |
| Server → client | `game.started`, `game.board.updated`, `game.action.result`, `game.score.updated`, `game.match.ended` | Match lifecycle, private board changes, action result, public scores, and final results. |
| Server → client | `error` | Stable protocol/game action error code and retry hint. |

The WebSocket connection must already be authorized by the Guest Session mechanism. Credentials are never placed in JSON messages. The exact HTTP session initialization contract and cookie policy are specified with W008.

## Ordering, correlation, replay, and versions

- `requestId` is generated by the client and is unique per session for the lifetime of an active Match. A response to a specific request echoes its `requestId` when the server can safely parse it.
- The server serializes state mutations in the owning Room event loop and assigns increasing `seq` values to Room events. A snapshot's sequence is its synchronization watermark. A client detects a gap and requests a fresh authorized snapshot.
- **PROPOSED for implementation design:** identical duplicate request IDs within the active Room/session return the cached terminal response without repeating side effects; reuse of an ID with different request content returns `ACTION_DUPLICATE`. W010 must implement bounded retention and document the cache lifetime.
- `boardVersion` and `referenceVersion` describe the sender's own Speed Battle board and reference card. They are not a shared Room revision. The server still checks Match membership, player eligibility, card availability, and authoritative matching rules.
- A successfully processed `game.pick_card` receives `game.action.result` with `accepted: true` and `outcome: "correct"` or `"incorrect"`. `accepted` means the action was authorized and processed; `outcome` is the gameplay result. A correct outcome is accompanied by the applicable score and private board updates. An incorrect outcome awards no points, resets the Combo, applies the required cooldown, and leaves score, board, and reference card unchanged. Its unchanged `boardVersion` and `referenceVersion` make that explicit; the client can still show Thai feedback from `outcome`.
- `game.action.result` only represents a processed pick, so its schema requires `accepted: true`. An `accepted: false` result is invalid; technical rejection uses `error` without a gameplay outcome.
- Technical rejections, including an action during cooldown, use a structured `error` and have no gameplay outcome. They do not trigger mistake penalties. Clients must distinguish these errors from a processed pick with `outcome: "incorrect"`.
- Match IDs ensure that messages from an earlier Match cannot affect a later Match. `seq` orders server events; it does not replace action-specific version validation.
- **PROPOSED for implementation design:** reject a v value other than 1 with `UNSUPPORTED_VERSION` when the envelope can be parsed; otherwise close the WebSocket with a protocol error. Do not silently reinterpret an unknown version.

## Privacy, validation, and error handling

- `room.snapshot` and `room.updated` contain Room participants and public readiness only. They do not contain player boards.
- `game.snapshot` is sent as a per-session projection. Its `cards` and `referenceCard` belong to `self`; `scores` contains only public scores. `game.board.updated` is sent only to the owner of that board. Never broadcast these private board fields to the full Room.
- Every envelope and nested object rejects unknown fields. The schema bounds identifiers, request IDs, codes, arrays, and card variants. Server-side business validation must additionally enforce Unicode grapheme username length, authentication, Room membership, Host authority, current Match state, rate limits, and active gameplay rules.
- The schema's Room Code bound accepts 1–12 uppercase alphanumeric characters. The requirement's six-character code is labeled an initial proposal; this schema does not promote that value to a confirmed rule.
- Preserve all error codes in §19.5. `retryable` informs UI behavior; clients must not automatically replay gameplay actions without request-ID idempotency. The client maps codes to Thai text and never displays server internals.
- **PROPOSED for implementation design:** W010 starts with a 16 KiB maximum UTF-8 text frame and bounded per-connection outbound queues. Confirm the frame-size value against actual snapshot payloads before release; oversize input fails closed.

## Compatibility policy

Version 1 is strict: required fields and allowed values are defined by the schema; extra fields are rejected. Additive changes therefore require a compatible v1 decision and coordinated deployment. Breaking envelope or payload changes use a new protocol version. The server should reject unsupported versions predictably. The protocol version is distinct from `boardVersion`, `referenceVersion`, and event `seq`.

## Contract validation

`pnpm protocol:check` validates all JSON fixtures under `fixtures/` with the committed schema. Valid fixtures must validate, and invalid fixtures must fail. Add a fixture for each new message type, error shape, boundary, or intentional compatibility change. CI runs this command before backend tests.

| Acceptance criteria | Fixture evidence |
|---|---|
| W005-AC-01 | Valid request, sequenced event/snapshot, correlated action result, and error fixtures. |
| W005-AC-02 | Invalid unknown property, unsupported version, and missing action version fixtures; every payload branch has bounded values and a closed object shape. |
| W005-AC-03 | Valid create/join/leave/ready/start/pick/snapshot request; correct and incorrect result; and Room/Match/score/result event fixtures. |
| W005-AC-04 | Pick request and both action-result outcomes include match, board, and reference versions; snapshot request carries its last observed sequence. |
| W005-AC-05 | Valid private game snapshot plus invalid `otherPlayersBoards` leakage fixture. |
| W005-AC-06 | Valid stable `STALE_ACTION` code fixture; schema enumerates all required §19.5 codes and protocol-specific codes. |
| W005-AC-07 | All fixtures run through `pnpm protocol:check`, also part of `pnpm check` and GitHub Actions. |
| W005-AC-08 | This document labels unapproved transport choices PROPOSED and schemas only the Speed Battle MVP. |

Both correct and incorrect processed picks have valid result fixtures. Invalid fixtures prove that results without an outcome or with `accepted: false` are rejected.
