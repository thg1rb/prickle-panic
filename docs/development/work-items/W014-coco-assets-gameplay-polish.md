# W014 — Coco Assets & Gameplay Polish

Status: READY_FOR_REVIEW  
Type: Frontend / Art / Audio Feature  
Owner: Project Owner assigns during execution  
Last updated: 2026-10-19

## Goals

- Replace W007's explicitly temporary procedural card visuals with a cohesive Coco's Berry Picnic asset set suitable for the playable Speed Battle MVP.
- Establish reusable, modular Coco construction so the 32 gameplay card variations share one character identity and remain visually consistent.
- Polish gameplay feedback, animation, sound, and responsive presentation while preserving card readability, accessibility, Thai-first UI, and authoritative gameplay boundaries.
- Record source files, provenance, licenses, attribution, usage restrictions, and review status for every production asset.

## Non-goals

- New gameplay mechanics, card attributes, scoring, Match timing, additional game modes, or changes to server authority.
- Independently generating 32 unrelated character illustrations.
- English localization, paid cosmetics, persistent inventory, or a full asset marketplace/pipeline.
- Replacing the React/Phaser architecture or adding an external asset hosting service without an approved requirement.
- Claiming an asset is commercially cleared solely because it was generated by AI; usage terms and provenance must be recorded and reviewed.

## Scope

- Production Coco character presentation and required MVP reactions: idle, correct pick, incorrect pick, combo, countdown, victory, defeat, and loading where practical. Not every animation is required if the approved vertical slice documents omissions.
- Modular character parts and compositional rules that preserve Coco's silhouette, proportions, palette, quill style, face, and distinguishing expression across card variants.
- Consistent rendering for the 32 binary-attribute combinations and all five gameplay attributes, without decorative accessories that can be mistaken for game attributes.
- Card faces, backs if used, UI illustrations/icons, lightweight woodland/picnic background treatments, and gameplay feedback visual states.
- Basic sound set required for MVP: background music, correct pick, incorrect pick, countdown, victory, volume and mute controls. Audio playback must respect browser gesture/autoplay behavior.
- Motion and UI polish integrated into the existing local prototype and later W011 online path without moving game rules or score authority into asset code.
- Responsive and accessibility refinement on desktop and mobile, including 320 CSS px viewport review, 4×4 card readability, reduced motion, keyboard/focus, semantic accessible controls, contrast, and non-color attribute cues.
- Asset manifest and source/provenance records stored in repository documentation or metadata, with editable sources retained where practical.

## Expected behavior

1. All player-facing asset-related copy, labels, feedback, and settings remain Thai. Visual or audio effects never convey a different rule than the authoritative state.
2. Each of the 32 cards is assembled from the same approved Coco base and modular attribute layers or a verified equivalent system. Given a card's five-bit identity, rendering is deterministic and visually maps each bit to the documented attribute without ambiguity.
3. Card readability takes priority over decoration: stable aspect ratio, rounded shape, clear hierarchy, no gameplay-attribute ambiguity, and redundant non-color cues. Cards remain operable by mouse, touch, keyboard and accessible controls.
4. Visual state feedback (correct, incorrect, combo, countdown, end/results) follows authoritative application state. Animation cannot alter, delay, or conceal card identity or create client-side score confirmation.
5. Reduced-motion preference disables or simplifies nonessential motion without losing gameplay information or competitive advantage. Essential state remains understandable without animation or sound.
6. Sound is optional and user-controlled; mute/volume settings work, and audio begins only after a suitable user interaction where the browser requires it. Audio must not be needed to perform an action.
7. The 4×4 board remains visible and readable at supported target widths without document scrolling where requirements demand it. If playtesting finds poor readability, record a proposed design change for owner review; do not silently alter board contents, count, or gameplay attributes.
8. Asset source files and a manifest identify each production asset's source, creator/provider, creation method, license/terms, attribution, restrictions, editable source path, and review/approval state. Generated assets include relevant prompt/reference provenance and generation tool/version when available.
9. No protected artwork/branding from other games is copied. Third-party assets are used only with a recorded license compatible with the intended project distribution; uncertain rights remain unapproved and are not shipped.
10. Asset loading failures show a Thai recoverable fallback rather than a broken game; decorative/audio failures cannot prevent gameplay or state recovery.

## Asset system and technical design

- Keep asset definitions separate from game rules. A shared asset catalog maps semantic names and card attributes to sprites/textures/audio, while W006/W011 remain the authority for variation identity and scoring.
- Prefer a small set of layered/vector sources and generated exports over 32 manually maintained composites. Use a deterministic build/export step only if it is reproducible, reviewable, and does not introduce unsafe remote scripts or undocumented dependencies.
- Define a stable asset naming scheme, directory layout, licensing metadata schema, and manifest validation procedure in technical design before bulk asset ingestion.
- Bundle MVP assets locally through the existing Vite build; no runtime third-party asset fetch is required. Optimize textures/audio size and loading without obscuring source provenance.
- Phaser owns gameplay canvas rendering and lightweight in-game animation; React owns navigation, Thai semantic UI, accessibility controls, and audio/settings controls. Keep asset adapter APIs usable by local W007 and online W011.
- Use Phaser animation/sprite assets or CSS for non-gameplay UI as appropriate; avoid duplicating state or allowing animation callbacks to mutate game state.
- Use vector or high-resolution sources where practical. Export production sprites at suitable density and texture atlas only where measurement justifies it. Preserve editable originals.
- Font files should be self-hosted when practical; include license and attribution notes. Verify Thai glyph coverage/fallback and avoid layout shifts while fonts load.
- Keep sound/music short, compressed, and optional. Provide user volume/mute controls and follow browser user-gesture restrictions.
- Testing validates all 32 visual mappings with deterministic fixtures, not artistic quality alone; visual acceptance also requires rendered evidence at desktop and mobile sizes plus owner/independent review.

## Asset review and licensing workflow

1. Record candidate and source before adding to production.
2. Review source authenticity, author/provider, license/terms, attribution, redistribution and commercial-use limitations, AI-generation terms, and any reference-image rights.
3. Record generation source tool/model/version if available, prompt/reference provenance useful for reproducibility, date, and generated/edited status. Do not retain or publish confidential prompts or restricted reference materials.
4. Inspect the editable source and exported asset for malware/unexpected embedded content when the format or source warrants; avoid executing untrusted asset scripts.
5. Review visual consistency, silhouette, Thai-context fit, attribute readability, accessibility/contrast, animation behavior, and mobile performance in the actual game layout.
6. Mark status PROPOSED, APPROVED, REJECTED, or NEEDS_REVIEW in the manifest. Only APPROVED assets may ship. A tool/service license does not imply the output itself has been reviewed.
7. Any material source, model, license, or asset change triggers manifest update and re-review; do not silently replace an approved asset with a different generation.

## Test and validation plan

- Deterministic mapping tests cover all 32 card variants and verify each of five attributes through non-color/semantic representation.
- Component tests cover asset loading fallback, Thai accessibility labels, correct/error/combo feedback state, mute/volume behavior, and reduced-motion rendering.
- Browser visual review captures desktop and 320 CSS px mobile layouts, card readability, no page overflow, keyboard/focus interaction, and Results/game states. Physical mouse/touch QA should be recorded separately from synthetic browser events.
- Verify Phaser scene cleanup and ensure no leaked canvases, texture/audio listeners, or animation timers across navigation/rematch.
- Verify autoplay behavior after user gesture, mute persistence as specified, and operation without audio device/playback.
- Inspect Vite production output and record asset bundle sizes and load behavior. Do not add performance claims without measured results.
- Run `pnpm check`, Go validation only where shared protocol/domain integration changes, security/license manifest validation, and relevant Playwright E2E. Report actual PASS/FAIL/NOT_RUN/BLOCKED evidence.
