# Architecture Decision Records

Create an ADR when a decision materially constrains architecture, security, deployment, protocol compatibility, or future implementation. Do not create ADRs for routine local choices or to restate an existing requirement.

## Process

1. Describe context and relevant requirement IDs.
2. State the decision and status: PROPOSED, ACCEPTED, SUPERSEDED, or REJECTED.
3. Record alternatives, consequences, security/operational impact, and migration implications.
4. Obtain Project Owner approval when a confirmed product decision changes or policy requires it.
5. Update affected architecture and feature specifications after acceptance.

Accepted ADRs are append-only records. Supersede an ADR with a new record and link both; do not rewrite history to hide a changed decision.

Use [`adr-template.md`](adr-template.md).
